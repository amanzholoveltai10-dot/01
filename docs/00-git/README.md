# Модуль 0. Git и GitHub: инструктаж с нуля

Цель модуля — чтобы к концу недели ты на автомате делал: ветка → коммиты → push → Pull Request → правки по ревью → merge.
Читай целиком, не по диагонали. Команды набирай руками.

---

## 1. Что такое Git и зачем он DBA

**Git** — система контроля версий. Она хранит историю изменений файлов: кто, когда, что и зачем поменял, и позволяет откатиться на любое прошлое состояние.

**GitHub** — сайт, на котором хранится копия твоего Git-репозитория и где удобно делать ревью (Pull Request-ы, комментарии к строкам).

Зачем это администратору БД, а не только программисту:

- **Конфиги под версионным контролем.** В реальной работе `postgresql.conf`, `pg_hba.conf`, скрипты бэкапов, роли и миграции хранят в Git. Когда в 3 ночи база легла после «маленькой правки», ты делаешь `git log -p postgresql.conf` и через минуту видишь, кто поменял `max_connections` и зачем.
- **Ревью изменений.** Ни одна правка `pg_hba.conf` в продакшене не должна попадать без второго взгляда. Одна лишняя строка `host all all 0.0.0.0/0 trust` — и база открыта всему интернету без пароля.
- **Инфраструктура как код.** Ansible, Terraform, Patroni — всё это тоже живёт в Git.

## 2. Как Git устроен «под капотом» (минимум, который надо понимать)

### Три зоны

```
  Рабочая папка         Индекс (staging)         Репозиторий (.git)
  (working tree)        «что пойдёт в коммит»     (история коммитов)
       │                        │                         │
       │ ── git add файл ──────►│                         │
       │                        │ ── git commit ─────────►│
       │◄──────────────── git restore / git switch ───────│
```

1. **Рабочая папка** — обычные файлы, которые ты редактируешь.
2. **Индекс (staging area)** — «черновик следующего коммита». Ты сам решаешь, какие изменения туда положить командой `git add`. Это позволяет из 5 изменённых файлов закоммитить только 2, которые относятся к одной задаче.
3. **Репозиторий** — скрытая папка `.git`, в ней вся история.

### Что такое коммит

Коммит — это **снимок (snapshot) всех файлов проекта** в момент фиксации + метаданные: автор, дата, сообщение и ссылка на **родительский коммит**. У каждого коммита есть уникальный идентификатор — SHA-хеш вроде `a1b2c3d…`, который вычисляется из содержимого. Поменяешь хоть байт — получится другой хеш. Поэтому историю в Git нельзя тихо подделать.

Коммиты связаны в цепочку: каждый знает своего родителя.

```
A ◄── B ◄── C        (main)
```

### Что такое ветка

Ветка — это **просто подвижный указатель (ярлычок) на коммит**. Не копия файлов! Создать ветку в Git стоит почти ноль ресурсов.

```
A ◄── B ◄── C              ← main
             ╲
              D ◄── E      ← hw/00-setup   (HEAD — «где я сейчас»)
```

Ты работаешь в ветке `hw/00-setup`, `main` в это время не меняется. Когда ревью пройдено, изменения из ветки **сливаются (merge)** в `main`.

`HEAD` — указатель «на какой ветке я сейчас нахожусь».

### Локальный и удалённый репозиторий

- **Локальный** — у тебя на компьютере.
- **Удалённый (remote)** — на GitHub. По умолчанию называется `origin`.

Они не синхронизируются сами! Ты явно отправляешь (`git push`) и забираешь (`git pull`) изменения.

## 3. Установка и первичная настройка

### Установка

- **Windows:** скачай Git for Windows с https://git-scm.com — при установке оставь всё по умолчанию. Работать будешь в «Git Bash».
- **Ubuntu/Debian:** `sudo apt update && sudo apt install git`
- **macOS:** `xcode-select --install` или `brew install git`

Проверка: `git --version`

### Представься Git-у (один раз на компьютер)

```bash
git config --global user.name  "Имя Фамилия"
git config --global user.email "почта-которая-указана-на-github@example.com"
git config --global init.defaultBranch main
git config --global core.editor "nano"     # или "code --wait" для VS Code
git config --global pull.rebase false      # pull делает merge — проще для начала
```

Зачем: имя и почта вшиваются в каждый коммит. Если почта не совпадает с той, что в GitHub-аккаунте, коммиты не привяжутся к твоему профилю.

Посмотреть настройки: `git config --global --list`

### Доступ к GitHub по SSH

GitHub не принимает пароль от аккаунта для `git push`. Нужен SSH-ключ (рекомендую) или токен.

```bash
ssh-keygen -t ed25519 -C "твоя-почта"      # Enter, Enter, можно задать passphrase
cat ~/.ssh/id_ed25519.pub                  # это ПУБЛИЧНЫЙ ключ — его можно показывать
```

Что происходит: генерируется пара ключей. **Приватный** (`id_ed25519`) остаётся только у тебя и никогда никуда не копируется. **Публичный** (`.pub`) отдаёшь GitHub-у. При подключении GitHub проверяет, что у тебя есть приватный ключ, парный публичному, — без передачи самого ключа по сети.

Добавь публичный ключ: GitHub → Settings → SSH and GPG keys → New SSH key → вставь содержимое `.pub`.

Проверка:

```bash
ssh -T git@github.com
# Hi <логин>! You've successfully authenticated...
```

> ⚠️ Если когда-нибудь закоммитишь приватный ключ, пароль или токен — это ЧП. Удалить файл новым коммитом недостаточно: он остаётся в истории. Ключ надо считать скомпрометированным и перевыпустить.

## 4. Ежедневный цикл работы

### Клонирование (один раз)

```bash
git clone git@github.com:amanzholoveltai10-dot/01.git pg-dba
cd pg-dba
```

`clone` скачивает весь репозиторий со всей историей и автоматически настраивает `origin`.

### Цикл на каждое задание

```bash
# 1. Встать на main и забрать свежие изменения (там могут быть новые задания)
git switch main
git pull

# 2. Создать ветку под задание и сразу на неё переключиться
git switch -c hw/00-setup

# 3. Работать. Постоянно смотреть, что происходит:
git status                  # какие файлы изменены / в индексе / новые
git diff                    # что именно изменено (ещё не в индексе)
git diff --staged           # что уже в индексе и пойдёт в коммит

# 4. Добавить в индекс конкретные файлы и закоммитить
git add homework/00-setup/environment.md
git commit -m "hw00: add environment description"

# 5. Отправить ветку на GitHub (первый раз — с -u)
git push -u origin hw/00-setup
# дальше в этой ветке достаточно просто:  git push
```

`-u` (upstream) связывает локальную ветку с удалённой, чтобы потом `git push`/`git pull` без аргументов знали, куда идти.

### Посмотреть историю

```bash
git log --oneline --graph --all     # компактное дерево всех веток — запомни эту команду
git log -p имя_файла                # история конкретного файла с изменениями
git show <хеш>                      # что было в конкретном коммите
```

### Исправить ошибки

```bash
git restore файл                    # выкинуть незакоммиченные правки в файле (осторожно, безвозвратно!)
git restore --staged файл           # убрать файл из индекса, правки в файле останутся
git commit --amend                  # поправить ПОСЛЕДНИЙ коммит (только если он ещё не запушен!)
```

Правило: **не переписывай историю, которую уже запушил** (никаких `--amend` и `push --force` на запушенных коммитах в этом курсе). Ошибся — сделай новый коммит с исправлением.

## 5. Как писать коммиты (на ревью буду придираться)

**Один коммит = одно логическое изменение.** Не «сделал всё задание одним коммитом», а несколько шагов.

Формат сообщения:

```
hw00: add PostgreSQL file locations

Collected data_directory, config_file, hba_file and current log
file via SHOW and pg_current_logfile() on Ubuntu 24.04, PG 17.
```

- Первая строка — до ~60 символов, в повелительном наклонении: `add`, `fix`, `describe` (по-английски) или «Добавить», «Исправить» (по-русски — тоже ок, но выбери один язык и держись его).
- Префикс `hwNN:` — номер задания.
- Пустая строка, затем (при необходимости) подробности: **зачем**, а не только «что».

Плохо: `update`, `fix`, `asdf`, `final`, `final2`, `правки`. Такие коммиты = `Request changes`.

## 6. Pull Request и ревью

**Pull Request (PR)** — запрос «влей мою ветку в `main`». Это главное место для ревью: я вижу diff, оставляю комментарии к конкретным строкам.

### Открыть PR

1. После `git push` зайди на страницу репозитория — GitHub покажет жёлтую плашку **Compare & pull request**. Либо вкладка **Pull requests → New pull request**.
2. **base:** `main` ← **compare:** твоя ветка.
3. Заголовок: `hw00: Git и рабочее окружение`.
4. Описание заполнится шаблоном из `.github/pull_request_template.md` — заполни все разделы.
5. **Create pull request** → пришли мне ссылку.

### Что происходит дальше

- Я оставляю комментарии и ставлю один из статусов:
  - **Request changes** — есть что исправить. Не мерджишь.
  - **Approve** — принято.
- Ты исправляешь **в той же ветке**:

  ```bash
  # правишь файлы
  git add ...
  git commit -m "hw00: fix log path for Ubuntu per review"
  git push
  ```

  PR обновится автоматически. Новый PR не нужен.
- На каждый мой комментарий ответь: либо «Исправил в <хеш>», либо аргументированно возрази. Молча проигнорированный комментарий = PR не принят.
- После Approve: на странице PR кнопка **Merge pull request** → затем **Delete branch**. Локально:

  ```bash
  git switch main
  git pull
  git branch -d hw/00-setup
  ```

## 7. Шпаргалка (её будешь гонять до автоматизма)

| Задача | Команда |
|--------|---------|
| Где я и что изменено | `git status` |
| Что изменено построчно | `git diff` / `git diff --staged` |
| Свежий main | `git switch main && git pull` |
| Новая ветка | `git switch -c hw/NN-name` |
| Список веток | `git branch -a` |
| В индекс | `git add путь` |
| Коммит | `git commit -m "hwNN: ..."` |
| Первый push ветки | `git push -u origin ветка` |
| Дерево истории | `git log --oneline --graph --all` |
| Отменить правки в файле | `git restore файл` |
| Убрать из индекса | `git restore --staged файл` |
| Куда смотрит remote | `git remote -v` |
